# 지식 위키 운영 규칙

`docs/wiki/`는 LLM이 유지하는 지속적 지식 베이스다. 이 문서가 위키의 **규범 문서**이며,
배경 자료인 [`about.md`](about.md)와 충돌하면 이 문서가 우선한다.

## 레이아웃

```text
docs/wiki/
|-- README.md         # 이 문서 (운영 규칙)
|-- about.md          # 배경 자료 (규칙 아님)
|-- index.md          # 카탈로그: 페이지별 한 줄 요약과 링크
|-- log.md            # 시간순 작업 로그, 추가 전용
|-- raw/              # 외부 원본 자료, 수집 후 삭제
`-- kb/               # 영구 프로젝트 지식
    |-- entities/     # 구체적 대상: 페이지, 도구, 외부 시스템
    |-- concepts/     # 추상적 주제: 워크플로, 관례, 접근성
    `-- decisions/    # 설계·아키텍처 결정, 날짜 기준
```

위키 작업에 필요한 파일이나 디렉터리가 없으면 먼저 만든다.

## 공간 분리

- `raw/`는 임시 원본 공간이다. 기사, 회의록, 보고서, 스크린샷 등은 원본 언어 그대로 보존하고
  수집이 끝날 때까지 수정하지 않는다.
- `kb/`는 LLM이 유지하는 영구 공간이며 본문은 한국어로 쓴다.
- 흐름은 `raw/` → `kb/` 단방향이다. 수집이 끝난 raw 원본은 삭제하고, `kb/` 내용을 raw로
  되돌려 복사하지 않는다.

## 작업

### 수집 (ingest)

1. 사용자가 `raw/`에 자료를 두거나 대화로 원문을 제공한다.
2. LLM이 자료 전체를 읽고 핵심 내용을 사용자와 맞춘다.
3. `kb/entities/`, `kb/concepts/`, `kb/decisions/` 중 알맞은 페이지를 만들거나 갱신한다.
4. 양방향 교차 링크와 깨진 링크를 보수한다.
5. `index.md`와 `log.md`를 갱신한다.
6. 사용한 `raw/` 원본을 삭제한다. 이 단계까지가 한 번의 수집이다.

### 질의 (query)

1. `index.md`에서 후보를 찾고 관련 kb 페이지를 읽은 뒤 인용을 포함해 답한다.
2. 색인에서 찾지 못하면 `rg -l "<키워드>" docs/wiki/kb/`로 전체를 검색한다.
3. 재사용 가치가 있는 답변은 kb 페이지로 저장하고 색인과 로그를 함께 갱신한다.

### 점검 (lint)

주기적으로 페이지 간 모순, 오래된 주장, 고아 페이지, 빠진 독립 개념, 깨진 링크, 조사할 정보
공백을 검사한다. 모순은 한쪽을 조용히 지우지 말고 양쪽을 기록해 `<!-- CONTRADICTION -->`
마커를 남긴 뒤 사용자에게 보고한다.

## 관례

- 파일명은 kebab-case `.md`다. decision은 `YYYY-MM-DD-{slug}.md` 형식을 쓴다.
- 고유명사로 지칭되는 대상은 `entities/`, 그 외 주제는 `concepts/`에 둔다. 판단이 어려우면
  `entities/`에 두고 관련 개념 페이지에서 링크한다.
- 위키 내부 링크는 상대 경로를 쓰고, 링크 텍스트는 한국어로 쓴다.
- 색인 항목은 페이지당 한 줄, `- [제목](경로) - 한 줄 요약` 형식이며 entities, concepts,
  decisions로 묶는다.
- 로그 항목은 `## [YYYY-MM-DD] {ingest|query|lint} | {제목}` 형식으로 `log.md` 마지막에
  추가한다. 오래된 항목이 위에 오도록 유지한다.

## Frontmatter와 출처

모든 kb 페이지는 다음 YAML frontmatter를 갖는다. 페이지를 갱신할 때 `updated`도 갱신한다.

```yaml
---
updated: 2026-08-17
tags: [static-site, accessibility]
---
```

모든 kb 페이지는 `## 출처` 섹션으로 끝난다. 외부 출처에는 제목, 저자, 발행일, URL, 수집일을,
내부 출처에는 제목, 작성 주체, 확정일, 저장소 상대 경로나 commit hash를 기록한다.

## Decision의 증분 기록

- 확정 decision은 당시의 근거와 결론을 보존하는 추가 전용 기록이다. 과거 결론을 변경하거나
  삭제하지 않는다.
- 결론을 번복하거나 범위를 바꿀 때는 새 날짜의 별도 decision을 만들고 대상, 변경 내용, 이유,
  적용 범위를 기록한다.
- 새 decision에서 이전 문서를 링크하고, 이전 문서의 관련 문장 바로 뒤에
  `(이 결정의 … 내용은 [후속 decision](경로)에서 조정됨.)` 형식의 최소 역링크를 추가한다.
  역링크만 추가할 때는 과거 decision의 `updated`나 로그를 바꾸지 않는다.

## LLM 규칙

- kb 페이지를 만들거나 고칠 때마다 같은 변경에서 `index.md`와 `log.md`를 갱신한다.
- 로그가 길어지면 필요한 구간만 `tail`이나 `rg`로 읽는다.
- 하나의 원본이 여러 페이지에 영향을 주는 것은 정상이다. 기록 작업을 생략하지 않는다.
- kb 페이지가 100개를 넘으면 로컬 마크다운 검색 도구 도입을 사용자에게 제안한다.
